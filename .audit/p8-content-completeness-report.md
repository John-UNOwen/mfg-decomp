# Content completeness (P8) — what was actually implemented, and how to re-check it

P8 ("implement, don't just document") shipped code and data files but no report: `.audit/`
held `p6-match-lifecycle-report.md` and probe scripts, and a glob over `**/*p8*.md` in the repo
returned nothing. Its verification lived in `tmp/p8repro/` (scratch) and in the transcript.
This file is the missing record: every finding traced to the change and the line it lives on,
with the checks re-run today.

Scope: the self-hosted plugin in `tmp/RyuNET-core/dist/plugins/mfg@asphyxia`. "client" means the
decompiled game under `api/recovered/Assembly-CSharp`, cross-checked against the reference
protocol in `mock/` (`Program.cs`, `specs/*.xml`). Nothing is committed.

## (a) Every GameEventType the client knows is now scheduled

**Client side.** `GameEventStatus.OnAfterDeserialize` seeds one inactive entry per
`GameEventType` and `GameEventData.OnAfterDeserialize` (`GameEventData.cs:76-85`) throws away any
row whose `name` does not parse to an enum member. A kind the server never names is a kind it can
never switch on: `EventStatus.IsActive(...)` stays false for it whatever the config says.

**Server side, before.** `ACTIVE_EVENTS` (01:06 snapshot, `utils.ts:1609`) was the server's own
table - 116 names - and `eventsJson` emitted exactly those, all active. The 35 names the audit
listed (`YellCampaign` → `YellGameData.cs:89-96`, `YakuBingo` / `YakuBingo3` →
`GameDataManager.cs:531-539` and `MissionFlow.cs:267-274`, `StoryAdditionShiori` →
`GameDataManager.cs:592-599`, plus `TenshiGowan`, `QRLogin`, `PaseliPointCampaign`, ...) were not
in it, so the yell campaign, the bingo event and its missions, and Shiori's story block could
never run.

**Now.** `data/event_kinds.json` carries the client's whole enumeration (304 names in declaration
order, `_source: GameEventType.cs`), regenerated by `scripts/gen_event_kinds.py`.
`eventKindNames()` (utils.ts:2223-2227) reads it, `eventsJson()` (utils.ts:2256-2268) emits one
row per name with `active/begin/end/param`, and `activeEventParams()` (utils.ts:2210-2221)
decides which are on: `BASE_EVENTS` (utils.ts:2115-2175) + the 77 `CostumeAdditionN` entries
(utils.ts:2181-2185) + the event-taku flags + `VFG_EVENTS_ACTIVE`. Answer `appli_info` at
`aog.ts:998-1006`. Measured: 304 rows, 117 active, 187 inactive with the far window
(2020-01-01 / 2099-12-31), so every gated kind is now reachable through config.

## (b) The mission schedule carries all 103 categories

`MissionDate.cs:42-45` loads `kind="missions"` through `MissionStatus.LoadFromJson`, and
`MissionData.OnAfterDeserialize` drops a row whose `category` does not parse to a
`MFG.Types.Mission.Category` member. Before, `MISSION_CATEGORIES` (`utils.ts:1413` in the 01:06
snapshot) was seven pairs with the comment "Event/dated categories are intentionally off" - the
other 96 categories were never named at all.

Now `data/mission_categories.json` holds all 103 entries of `Category.cs` in enum order
(`_source` records that; `scripts/gen_mission_categories.py` regenerates it), `missionsJson()`
(utils.ts:1974-1984) emits `Category` ints matching the enum order plus `category` names,
`active`, `begin`, `end`, `param`, and `missionRowActive()` (utils.ts:1965-1972) applies
`VFG_MISSION_ACTIVE` (`all` / `none` / a name list that adds to the defaults). `handle_mission_date`
at `aog.ts:2548-2550`. Measured live: 103 rows, `Category` 0..102 in order, seven active -
`JudgmentDaily, JudgmentWeekly, Player, Character, Weekly, Yaku, StartDash` - the dated ones
present and inactive.

## (c) Notice content is authored, and the acks now filter something

`NoticeGameData.Save()` is never called anywhere in the assembly, and `ReceiveOnlyGameData` has no
`Save` at all: an account's notice list exists only if the server wrote it. The audit found both
halves broken - `handle_client_state_read` serving only states already stored with zero
`notice_game` documents in the whole database, and `notice_done` / `important_notice_done` answering
an empty serv_st while throwing the posted `done_ids` away. By the 01:06 snapshot the ack half was
already in place (`handle_notice_ack` persisting the buckets, `aog.ts:2466-2483` there), but with
nothing ever authored it filtered an empty list: `notice_game` and `receive_only` were not mentioned
anywhere in the read path (grep of the snapshot: zero hits), so `HomeNoticeWindow.cs:131/189`, the
new-notice lookup at `HomeFlow.cs:956` and the carousel at `HomeFlow.cs:1004` had nothing to show.

Now: `data/notices.json` (3 notices with the client's own `NoticeInfo` fields, 2 important ids
that are `MFG.Types.ImportantNotice.NoticeID` members Manner=1 / Nuisance=2, because
`ImportantNoticeWindow.cs:52-55` looks its page up by that name and skips ids its master does not
have). `serverNoticeDocs()` (utils.ts:1797-1831) maps them, `importantNoticeIds()` (utils.ts:1836-1844)
maps the ids, `ackedNoticeIds` / `noticeGameJson` / `receiveOnlyJson` (utils.ts:1846-1880) drop the
ids this profile has already acked, and `seedServerOwnedState` (aog.ts:818-833) re-authors both on
every `client_state_read` (aog.ts:1188-1200) and writes only when the document actually differs.
`handle_notice_ack` (aog.ts:2824-2841) persists `done_ids` on the profile, routed at
aog.ts:2902-2903.

Measured on a never-used account (`.audit/probe_notice_p8.py P8NOTICE0001`, no acks posted):
`notice_game` ids `[1, 2, 3]`, `receive_only.ImportantNotices` `[1, 2]`, and the stored documents
in `dist/savedata/mfg@asphyxia.db` match (`.audit/p8_peek_profile_state.js`). After
`notice_done 1,2` the list is `[3]`; after acking 3 it is `[]`, and the empty list is what a later
read serves.

## (d) Name and sticker screening runs off a real list

`TABOO_WORDS: string[] = []` (01:06 snapshot, `aog.ts:2485`) with `isTaboo()` next to it made
`/chk_tabooword` answer `result 0` for everything, which `ChkTabooword.cs:34-37` reads as "name
available" and `NewRegistrationFlow.cs:243-259` accepts.

Now `data/taboowords.json` (37 entries) is loaded by `TABOO_WORDS` (utils.ts:1922-1935), which
also appends `VFG_TABOO_EXTRA` and logs loudly if the file comes up empty; `isTabooText()`
(utils.ts:1937-1942) is a case-insensitive substring test on the trimmed value. It is applied on
all three paths a bad string reaches the server through: `/chk_tabooword` (aog.ts:2848-2853),
table stamps posted by `gchat` (aog.ts:2112-2121 - name and sticker screened, the sticker is
dropped and the name blanked rather than the request failing), and the second stamp path
`gget_stamp_info` (aog.ts:2143-2151). Matching is a substring test, so the file deliberately
carries only entries long enough not to catch an ordinary word (`MeldBonus`, `TableSticker001`
pass clean; `死ね` is screened too).

## (e) chara_enabled answers where the client reads

`CharaEnabledSend.cs:34-37` reads `is_gacha_enabled` and `end_date` off `<root>`; the old answer
wrapped them in `<chara_enabled>` (01:06 snapshot, `aog.ts:2591-2598`), `Element()` returned null,
the parse fell through the bare catch at `CharaEnabledSend.cs:39-41`, and
`GachaSelectFlow.cs:912` never opened the pickup-gacha notice. The gate value itself was already
computed from the banner schedule (`pickupGachaGateActive()`, utils.ts:1277 - on exactly when an
advertised banner has a Pickup pool behind it); what changed is that the answer arrives where the
client looks. Now the two fields are emitted at the root (aog.ts:2963-2976) and `end_date` is the
schedule window in the `YYYY-MM-DD HH:MM:SS` shape `DateTimeOffsetManager.GetJSTFromString` parses,
not the `2099-12-31T23:59:59+09:00` the old handler sent.

Live: `<root><serv_st><code>0</code></serv_st><is_gacha_enabled>1</is_gacha_enabled><end_date>2099-12-31 23:59:59</end_date></root>`.

## (f) competition_entry answers the shape the client parses

`CompetitionEntry.cs:44-60` looks for two root containers, `<entry>{result,is_entry,reason}` and
`<displayed_result>{result,is_check_result}`. Before, the server sent
`<competition><entry_result>1</entry_result></competition>` (01:06 snapshot, `aog.ts:2408`): both
lookups missed, `IsEntried` stayed false, and every entry-gated branch
(`CompetitionEntryWindow.cs:148-163`, `CompetitionGameData.cs:58/70/124/174`, `HomeFlow.cs:1040`)
kept routing back to the entry scene. Now the answer carries both containers with their full
child sets, matching `mock/specs/competition_entry.xml` (aog.ts:2759-2767), and
`competition_game` is authored as an empty account record so the entry state is at least
representable.

Live, both modes (`compe_id=3` and `compe_id=3&displayed_result=1`):
`<entry><result>1</result><is_entry>0</is_entry><reason></reason></entry>` plus
`<displayed_result><result>1</result><is_check_result>1</is_check_result></displayed_result>`.

## (g) The state kinds only this server can write are written

`ClientStateRead.cs` can load kinds that no client-side `Save` ever posts back, so they exist on an
account only if the server authored them. Before, `handle_client_state_read` emitted stored kinds
only, and `receive_only`, `competition_game`, `competition_latest_result`,
`shop_competition_game`, `shop_competition_latest_result` were never present - those features ran
on client defaults forever.

Now `SERVER_OWNED_STATE_KINDS` (utils.ts:1886-1893) names them, `serverOwnedStateJson()`
(utils.ts:1895-1911) authors them (`receive_only` with the penalty flag, the campaign info and the
important notices; the four competition records as empty account records for a server that runs no
competition), and `seedServerOwnedState()` (aog.ts:818-833) rebuilds them on each read, writing
only on change. `music_gacha`, `present_box_game` and `friend_game` have their own authoring paths
in `aog.ts` and belong to the gacha / present-box packages (what the music gacha asserts is written
up in `.audit/README.md`). `friend_game` used
to be thrown away on read and replaced by a synthesized list that marked every entry usable;
now `seedFriendGameState` (aog.ts:1456) seeds once and then keeps the stored document, and the
rows come from `borrowableLender()` (aog.ts:1394-1430) - the same test the borrow endpoint applies
- so an `IsUsable` row is a servable borrow. `EnableOdekake` is back in `BASE_EVENTS`
(utils.ts:2148-2155; it was commented out at `utils.ts:1592` in the 01:06 snapshot), without which
`MyRoomMainWindow.cs:102` never shows the Friend page at all.

Writes to kinds the server owns are refused rather than believed: `client_state_write` answers
`serv_st 803` (`StatusCode.DataError`) for `receive_only` (aog.ts:1648) and `music_gacha`
(aog.ts:1634); the client's own `Save` call sites catch that and flag `IsDataSaveFailed`
(`PlayerGameData.cs:440-444`), so nothing is acknowledged that did not land.

### The reason a re-check of P8 failed, and what was done about it

`verify_p8.py` used to run under one pinned account name (`P8VERIFY00001`). Notice acks are
permanent per profile by design, so once that account had acked notices 1, 2, 3, the run passes
exactly once and then fails the same 5 notice checks every time - recorded in
`.audit/p8_content_sweep_exhausted.out.txt`:

```
FAIL notice_game carries the client's NoticeInfo fields   ids=[]
FAIL notice content is served                             ids=[]
FAIL important notices are the client's own NoticeIDs
FAIL acked notices are gone from notice_game              ids=[]
FAIL one_kind=notice_game is served after the acks
```

Those 5 failures are the fixture, not a regression: the same script on a name the server has never
seen passes 54/54, and the fresh account probe above shows `[1,2,3]` on first read. The same trap
the `.audit/README.md` already documents for the music gacha. The sweep now rotates its default
account (`tmp/p8repro/verify_p8.py`, header) and pins one only when you pass it as `argv[1]`.

## Judgement calls worth knowing about

- **The 187 inactive event kinds and 96 inactive mission categories are scheduled, not switched
  on.** Naming them is what makes them reachable: `VFG_EVENTS_ACTIVE=YellCampaign,YakuBingo,
  StoryAdditionShiori` and `VFG_MISSION_ACTIVE=Bomb,Competition9` both work (verified in the config
  check above). They stay off by default because the flag is only the client's gate - what appears
  behind it is content and state this server does not author, so a switch that is not backed by
  content shows a feature with nothing in it. Deployment decision, not an oversight.
- **`competition_entry` answers "request ok, not entered".** The server runs no competition, and
  `competition_game` is authored as the empty record that says so. `CompetitionEntryWindow.cs:148-152`
  stores `IsEntried` straight from `is_entry`, so `is_entry 0` is the honest answer for a server with
  nothing to enter; the `IsEntried = false` at `:157` is only the communication-failure branch.
- **Notice acks are permanent** (`notice_done_ids` / `important_notice_done_ids` on the profile,
  capped at 400 entries, aog.ts:2835). There is no expiry, no read-state sync across accounts, and
  a notice id reused later stays invisible to accounts that already read it.
- **No home banners.** All three notices have `home_display` false and no `HomeBannerName`, because
  `NoticeInfo.IsDisplayHomeBanner` (NoticeInfo.cs:57-64) drives a forced modal and a carousel asset
  this client build must actually have. Plain list entries only.
- **Taboo matching is a substring test on the trimmed lowercase value**, applied to names and to
  table stamps; entries are chosen so ordinary words survive. Blank, not reject, is what a stamped
  message gets (`gchat` keeps the row, drops the sticker and blanks the name).
- **77 `CostumeAdditionN` kinds are active by default** so every costume in the client master can
  appear in My Room; unlocking still costs fight spirits client-side.
